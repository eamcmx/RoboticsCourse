Inverse of a homogeneous transform

If T sends a vector from frame B to frame A, T⁻¹ sends it back. There is a beautiful shortcut — you almost never need to call a generic matrix-inversion routine.

Why we need the inverse

Often we know a vector in frame A and need it in frame B — the opposite direction of the transform we have. We need T⁻¹.

We've been talking about going from a mobile frame to a fixed frame. But the other direction comes up constantly. The robot's controller knows the end-effector pose in the base frame and needs to know it in the tool frame to interpret a sensor reading. A camera mounted on the wrist sees the world in its own frame and we need it in the workspace frame. Both are inverse-transform problems.

For a 4×4 matrix you could in principle call a Gaussian-elimination routine. We never do. The structure of T gives us a much simpler answer.

The trick

A rotation matrix R has a special property: R⁻¹ = Rᵀ. The inverse is just the transpose. That's because R is orthogonal — its columns are orthonormal unit vectors, so RᵀR = I. Inverting a 3×3 by transposing it is essentially free.

The rotation block flips to its transpose; the translation block becomes −Rᵀ·p. No determinant, no cofactor expansion, no LU decomposition. Just a transpose and a small multiplication.

Visual round-trip: T then T⁻¹

If our derivation is right, applying T and then T⁻¹ should leave any frame exactly where it started. The widget below tests that claim live: a third frame is rendered at the round-trip destination — if our T⁻¹ is correct, it always overlaps the fixed frame, no matter what you do with the sliders.

The widget shows three frames in the same scene:

  • The fixed frame (red/green/blue) at the origin.
  • The mobile frame B (orange/purple/cyan) at T, driven by the six sliders.
  • A round-trip frame (faded blue), rendered at T⁻¹·T applied to the fixed frame. If the math is correct, T⁻¹·T = I and the round-trip frame sits exactly on the fixed frame, regardless of what T is.

Drag the sliders. The mobile B will move all over the place; the round-trip frame should never move. The numeric T and T⁻¹ matrices on the side update live so you can read off both at every pose.

Read the tracked point

The tracked point lives in frame B at coordinates (0.4, 0.3, 0.5) — those don't change. Below the sliders you'll see the same point's coordinates in the fixed frame (T·a_B), and then T⁻¹ applied to those fixed-frame coordinates. The "T⁻¹·(A-coords)" line should always read (0.4, 0.3, 0.5) up to floating-point precision. That's the round-trip in numeric form.

Why it works algebraically

There's a clean geometric reading of the formula. T sends frame B's basis vectors into frame A. To go back, we need to undo the rotation (transpose) and undo the translation. But the translation has to be expressed in B's coordinates now, because we're going from A back to B. That's why p, originally a vector in A, gets pre-multiplied by Rᵀ before being negated.

Mechanically, you can verify it by multiplying T·T⁻¹ block-by-block:

R·Rᵀ = I, and the translation telescopes to zero. The product is the identity, as required.

Implement and verify in code

We will package the shortcut as a small function inv_T(T). It pulls out R and p, transposes R, and assembles the new transform — a routine you'll reuse on every robot in this course.

Build the function in the sandbox. The math.js syntax for transpose is R'; for matrix multiplication, *. Pull the rotation block with T[1:3, 1:3] (math.js uses 1-based indexing) and the translation column with T[1:3, 4].

Floating-point reality check

The product won't be exactly the identity — you'll see entries like 1.0000 and 0.0000 with tiny non-zero residues at the 10⁻¹⁵ scale. That's normal floating-point error from sin/cos rounding, not a bug. The sandbox already cleans values below 10⁻¹⁰; if you ever doubt a result, multiply by a cleanup function that zeros anything smaller than 1e-10.

Quick recap

  • For a rotation matrix R, R⁻¹ = Rᵀ. Orthogonality gives you the inverse for free.
  • For a homogeneous transform T = [R, p; 0, 1], the inverse is T⁻¹ = [Rᵀ, −Rᵀp; 0, 1].
  • Verify: T · T⁻¹ should give I₄ within floating-point precision.
  • Use this whenever you need to go "the other way" between two frames — never call a general matrix-inversion routine on a homogeneous transform.
Homework 04 · due before next session

Write your own inv_T, prove it works

  1. By hand: write the inverse of T = [Rz(45°), (1, 2, 3); 0, 1] using the shortcut. Show the symbolic Rᵀ and the −Rᵀp computation step by step.
  2. Implement inv_T as a MATLAB function (or a math.js function in the sandbox if you prefer). It should take a 4×4 and return a 4×4.
  3. Test on three different transforms — pure rotation, pure translation, mixed. For each, verify norm(T · inv_T(T) − I) < 1e-10.
  4. Compare your inv_T against MATLAB's generic inv() on a homogeneous transform — they should agree to floating-point precision. Time both for a million calls. Report the speed-up.
